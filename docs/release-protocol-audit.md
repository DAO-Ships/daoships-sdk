# Protocol and deployment release audit — 2026-09-10

The SDK remains focused on DAOShips. No QuaiVault SDK dependency or CLI functionality was added. Review covered deployment discovery, launch encoders and salt mining, deployment orchestration, all eight navigator wrappers, governance, chain snapshots and preparations, token/permit/ragequit conveniences, and vault module traversal. Solidity and web-app projects were inspected read-only.

## Findings fixed

| Severity | Finding and evidence | Resolution |
| --- | --- | --- |
| Medium, correctness/availability | `resolveVaultModulePredecessor` treated `getModulesPaginated.next` as the last returned module. Actual QuaiVault `_getModulesPaginated` starts at `modules[start]` and returns the first unreturned module as `next`. With page size one and list A → B, the old traversal skipped B. It could report absence or derive an invalid predecessor. Previous unit fixtures encoded the wrong pagination semantics. | `src/vault.ts:58` validates page continuity and advances from the last returned module. Corrected fixtures model actual linked-list behavior. Local acceptance tests query the real source-verified QuaiVault with page size one across the DAO and Budget module entries and verify confirmed absence. |
| Medium, availability/input handling | `Navigator.read` and `simulate` bypassed the deadline, cancellation, response-size and ABI validation protections available through `ContractClient`. A hung provider never settled; malformed dynamic ABI values could escape as deferred errors. | `src/provider-call.ts` supplies one shared bounded call transport for both APIs. Navigator reads reject deferred ABI errors. Read options expose normal transport/input limits; simulation accepts an optional final options argument. Transport failures remain `CHAIN_ERROR`; malformed ABI results are `INVALID_RESPONSE`. |
| Medium, deadline enforcement | A synchronous provider could block the event loop longer than the deadline and resolve through a microtask before the timeout callback ran. | Monotonic elapsed-time checks reject late successful results in contract/navigator calls, chain reads, deployment discovery/workflows and permit discovery. Regression providers deliberately block briefly, then resolve successfully. Cancellation/deadlines cannot preempt synchronous JavaScript or shut down caller-owned providers. |
| Medium, RPC efficiency | `prepareVotes` accepted unbounded arrays and launched two concurrent RPC reads per proposal. | `src/chain.ts:298` limits this convenience to 1000 votes and reads eight proposals per batch, at most 16 simultaneous calls. Inputs must be dense own data entries and are captured before RPC. Generic contract encoding remains available. Ragequit selection is capped at the protocol's 20 guild tokens. |
| Low, deterministic preparation | Multi-phase salt mining reread mutable caller options, singletons and vault owners after yields. Progress callbacks could mix deployment identities between phases. | Mining captures options and nested configuration before yielding. A regression mutates sender, factory, singletons and vault owners during progress and verifies original predictions. Launch type and ABI constants are now frozen. |
| Low, RPC integrity | Deployment discovery accepted any truthy block hash, including truncated identifiers used by its original fixtures. | Discovery requires a 32-byte mined hash and a valid block number, including structured errors for missing headers. Fixtures now use valid block identities. |
| Release-policy gap | Workflow verification/reconciliation had no explicit confirmation-depth policy beyond one mined canonical receipt. | `DeploymentVerificationOptions.confirmations` and workflow run options accept 1–10000, default 1. Insufficient depth yields `TX_PENDING` without a broadcast or checkpoint promotion; invalid policy is rejected before execution. Verified steps are rechecked against the supplied policy on resume. This is zone-block depth, not a proof of Quai finality. |

## Contract and application alignment

All eight navigator activation plans still use DAO governance. Budget emits the same vault `enableModule` self-call used by `daoships-app/src/utils/budgetProposals.ts`; ordinary DAO role mutations use `executeAsGovernance`. Independent vault-owner authorization remains confined to bootstrap of existing vaults. Signal endorsement still requires a complete caller-authenticated current set, because Poster stores events rather than an authoritative current set in contract storage.

Source review confirmed DAO proposal module checks, defeated-proposal empty-data handling, retention math, token supply bounds, treasury-before-transfer accounting, the eight navigator role requirements, and launcher CREATE2 sender distinctions. The SDK does not duplicate vault owner voting or signing policy.

One upstream integration discrepancy remains: app creation bytecode differs from the current source-verified SDK artifacts for Onboarder, ERC20Tribute, NFTGated and Signal. Direct comparison after removing trailing Solidity CBOR metadata shows executable creation-bytecode differences for the first three; Signal differs only in metadata. This is not evidence that deployed contracts have those versions. Resolve artifact provenance before asserting web-app/SDK deployment parity; sibling projects were not changed.

## Validation and remaining release limits

The full coverage run before the final confirmation-depth addition passed with 98.43% lines, 93.16% branches and 98.85% functions, above unchanged 95/85/95 gates. Subsequent focused deployment and contract suites passed, including confirmation-depth reconciliation. The actual-contract local deployment suite passed all three launch routes, all eight DAO-governed activations, and the new real-vault pagination regression. `sync-navigators.mjs --check` verified all eight source-current SDK artifacts. The coordinating release report records the final combined suite after all agents' changes.

No unresolved critical/high finding was established in this reviewed SDK scope. Production readiness still requires live Quai acceptance for native CREATE/grinding, actual wallet/provider behavior and chosen confirmation policy; honest providers and reviewed deployment addresses; a durable atomic store shared by account users; and application-authorized executors with recovery for each proposal/approval/processing transaction. Local EVM acceptance does not establish those operational properties or replace an independent security audit.
